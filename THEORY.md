# A Theory of obsidian-periodic-notes

## What this system is for

Obsidian stores notes as Markdown files in folders. It has no concept of time. Users want to think in dates — today's note, this week's note, the month before this one — and this plugin is the bridge: it establishes the convention that **a file whose path renders from a Moment format string _is_ the note for that date at that granularity**, then maintains that mapping, makes it fast to query in both directions, and hangs three affordances off it (ribbon, commands, a sidebar calendar).

The domain has four entities. A **granularity** is one of day, week, month, year. A **note config** binds a granularity to three parameters: a format string, a folder, and an optional template. A **cache entry** is one file's claim on one period. The **index** is the live bidirectional map — path to period, period to path. Everything else is downstream of two lookups: given this file, what period is it; given this period, what file is it.

**The single fact that shapes the most code is not technical.** The README states it plainly: this is personal tooling with one known installation, forked from `liamcain/obsidian-periodic-notes` and no longer a drop-in replacement. That licence to break things is why the plugin does things a general-purpose plugin cannot. There is **no settings migration** — `sanitizeSettings` reads whatever JSON is on disk, type-checks each field independently, and falls back to the default for anything it does not recognise. A v1 user upgrading silently gets fresh defaults, and that is the intended behaviour, not an oversight. Features get **deleted** rather than deprecated: quarter granularity, the quick switcher and the NLDates dependency all went, each in a version that shipped without a compatibility path. And verification is **one vault**, not a test matrix — which is why the code carries so much defensive commentary about event ordering that no test exercises. If you inherit this and start adding migration shims or upstream compatibility, you are working against the grain.

## The organizing ideas

**The format string is the schema.** There is no metadata store. The date is derived from the path by parsing it against the configured format, and that one string does triple duty: it generates new filenames (`date.format(format)`), it recognises existing ones (`moment(input, formats, true)`, always strict), and it defines the uniqueness constraint, since two files whose paths parse to the same `startOf(granularity)` are claiming the same period. This is why changing a format makes every existing file invisible to the index until renamed, and why `validateFormat` refuses a format whose _rendered sample_ contains `..` — an unrecognised token passes through literally, so `[..]/YYYY` only reveals its traversal once formatted.

**A format can nest, which is where the one genuinely non-obvious abstraction lives.** `getPossibleFormats` returns two candidates for a format containing `/`: the whole thing, and the part after the last slash. Next to it, `extractDateStringFromPath` sometimes returns the file's basename and sometimes returns the last N path segments. Neither makes sense alone; together they cover the two shapes a nested daily format can take. `YYYY/YYYY-MM-DD` puts a self-describing name in a year folder — the basename alone identifies the date, so extraction returns the basename and the _partial_ candidate parses it. `YYYY/MM/DD` does not — a basename of `12` identifies nothing, so `isFragileBasename` says so, extraction walks back up as many segments as the format has, and the _full_ candidate parses `2026/06/12`. That is the whole reason for both the second candidate and the fragility check, and it is why the check is day-only: week, month and year formats are always read from the basename.

**`match` is provenance, and it governs four separate decisions.** A `CacheEntry` records _why_ the file counts — because its path parses (`"filename"`) or because a frontmatter property named after the granularity claims it (`"frontmatter"`). This is not merely an escape hatch. It decides (1) that `resolveEntry` refuses to re-resolve a path already matched by frontmatter, (2) that a frontmatter match **survives a rename** while a filename match is re-resolved, (3) that frontmatter wins a collision in `preferred`, and (4) that a file whose frontmatter is edited away is removed and re-offered to filename matching rather than silently dropped. A maintainer who does not hold this will break one of the four while fixing another. The refusal in (1) is what makes the outcome **order-independent**: `initialize` offers each file to the filename matcher and then the frontmatter matcher, but flipping that order converges on the same entry, because the second call would refuse. Do not treat the sequence in `initialize` as load-bearing; the rule is.

**The index is a hint, verified on every read.** `CacheIndex` keeps `byPath` and `byKey` over the same entries, and it can outlive the files it points at — one missed or out-of-order delete event is enough. Rather than trying to keep it perfectly true, every public read on `NoteCache` funnels through `fileFor`/`verify`, which resolves the entry against the vault and drops it if the file is gone. **This is what makes invalidation allowed to be sloppy**, and it is the property a new read method most easily destroys: add a public getter that touches `this.index` directly and you have reintroduced staleness that nothing else in the class can suffer from. `findAdjacent` needs a loop rather than a single check for the same reason — a stale neighbour must not end the search, or "jump forwards" fails silently past a deleted note.

**One file per period, decided by rule rather than by arrival.** `byKey` holds a single entry per canonical key, so two notes claiming one period is a real conflict. `preferred` resolves it: frontmatter beats filename, and failing that the lexically smaller path wins — arbitrary but stable, which the vault walk order was not. The loser is dropped from `byPath` too, not just `byKey`, because `byPath` backs `get`, `has` and `findAdjacent`, and leaving it there would report a note the calendar and nav commands cannot act on. `set` therefore returns _whichever entry now holds the key_, and callers check: `resolve` compares the returned `filePath` against its own before announcing anything. Being dropped is not the same as being forgotten: the loser is filed in `contenders`, a third map keyed the same way as `byKey`, and whenever a key is freed — by `remove`, or by `set` re-dating the entry that held it — the best remaining contender is promoted into it. Only losers are recorded, so a vault with no collisions carries no extra state — and because the promoted entry is never checked against the vault, a promotion that resurrects a deleted file is corrected by the next read, which is the same self-heal every other read already relies on.

**Keys are ISO timestamps behind a granularity prefix, so lexical order is chronological order.** That is the only reason adjacency can be a binary search over a plain sorted array of strings, with the sorted arrays cached per granularity and invalidated by a dirty set. It also means `canonicalKey` throws rather than tolerating an invalid moment: `toISOString()` returns null for one, the template literal would render `"null"`, and every invalid date in a granularity would alias to a single key.

**The calendar is a projection of the index, refreshed by a counter.** Nothing in `src/calendar/` queries the vault. `CalendarStore` exposes a `$state` integer whose _value_ is meaningless and whose _changes_ are the signal; five vault and workspace events increment it, and `Calendar.svelte` reads it inside a `$derived.by` — `void fileStore.version` is the entire subscription — to recompute one `FileMap` covering all fifty cells the current view needs. Children do synchronous `$derived` lookups into that map. The store's `bump` is deliberately unguarded: filtering on `cache.isPeriodic` cannot work after a delete or rename, since the entry is already gone by then, and because reads self-heal, an occasional wasted recompute of a fifty-entry map is cheaper than the correctness argument the guard required.

**Obsidian owns anything with a confirmation dialog.** The calendar's context menu contributes _no items of its own_ — it constructs a `Menu`, triggers `file-menu`, and shows the result, so Delete arrives from core with its confirmation and the vault's own "Deleted files" preference, alongside Rename and whatever other plugins add. The item that used to sit there called `vault.trash(file, true)`, hard-coding the system trash regardless of the user's setting. Read this as a general posture: where core has a behaviour with user-facing policy attached, defer to it rather than reimplement it.

## The seams

**Against Obsidian.** The plugin declares two custom workspace events in `obsidian.d.ts`: `periodic-notes:settings-updated` (fan-out for a settings change that affects indexing) and `periodic-notes:resolve` (a file has been recognised as periodic). The second is the plugin's public API for other plugins, and its contract is specific — it fires **after** the template has been applied on the create path, so a listener may read file contents. Anything that moves that trigger earlier breaks a promise made outside this repository.

**Lifecycle is a seam that has bitten.** `NoteCache` is attached with `addChild`, not assigned to a field, because `Component.registerEvent` only arranges teardown during the component's _own_ unload — without it the cache's listeners survive a disable, and a disabled plugin goes on applying templates. `configureLocale` returns its undo function and is handed to `register` for the same class of reason: `moment.locale()` is a global setter on the single instance Obsidian shares with every plugin, so leaving it set reconfigures date formatting for the whole app. Both are cases where the framework's default is _leak_, and the correction is invisible until someone toggles the plugin.

**Between the index and note creation.** Template application is triggered from inside `resolve`, because the cache is the one place that knows "this file just became a periodic note." The dependency runs `main → cache → template → templateRender`, a DAG, but it means the cache is also the creation-side orchestrator. `resolve` is `async` only for this, and the `await` splits it: three guards protect the trigger — this file lost a collision, the file was deleted mid-write, the file was renamed mid-write — each refusing to announce something a listener could not act on.

**The pure/impure line.** A module that imports a _value_ from Obsidian cannot be imported by a test at all, since Obsidian is the host application and not a package. Every core/wiring pairing in the tree exists to move logic across that line: `cacheResolve`, `cacheFrontmatter`, `cacheIndex`, `cacheSearch`, `paths`, `settingsLoad`, `format`, `templateRender`, `locale`, `calendar/store`, `calendar/utils`. Eleven modules have tests; the rest are verified by loading the build into a vault. This boundary is principled and worth defending — when logic needs testing, the move is to extract it, not to build an Obsidian mock, and the injected callbacks (`normalizeFolder` into `sanitizeSettings`, a frontmatter `read` into `resolveFrontmatterEntry`, `getFile` into `computeFileMap`) are how that extraction is paid for.

**Where the vault boundary is enforced, twice.** `paths.ts` refuses traversal, and it treats a **backslash as a separator** — Obsidian's `normalizePath` converts backslashes to slashes, so checking only `/` would let `..\..\x` through as one innocent segment and let normalisation turn it back into a traversal afterwards. The check runs at the settings boundary (reject, do not persist), at load (refuse, keep the default), and in `buildNotePath`, which throws immediately before `vault.create`. That is defence in depth on purpose: the settings tab can be bypassed by hand-editing `data.json`.

## What accommodates change, and where damage happens

**Cheap.** A new template token for an existing granularity; a new per-granularity settings field; calendar styling; new commands, which are produced by a factory per granularity.

**Structural.** A fifth granularity touches the `Granularity` union, `granularities`, three constant tables, the label maps, and the settings and command loops — the type system walks you through nearly all of it, but the calendar assumes a month grid with weeks inside, so a quarter view is new layout work. Supporting **two files for one period** is not a change but a redesign: one-per-key is enforced in `set`, the `FileMap` stores `TFile | null`, `getPeriodicNote` returns `TFile | null`. **Replacing Moment** is likewise structural — format strings, `startOf` normalisation, locale configuration, token parsing and the calendar's date arithmetic all use it directly, through a global, with no wrapping layer.

**Three places a maintainer without the theory does damage.**

The first is the calendar's **two enabled signals**. `Month.svelte` derives `monthEnabled`/`yearEnabled` from `fileMap.has(key)` — presence in the map _is_ the enabled signal there — while day cells are switched off by an explicit `dayEnabled` prop, and `computeFileMap` maps every day unconditionally. That reads as an inconsistency begging to be unified, and unifying it is a bug: `Day.svelte` reads `fileMap.get(key) ?? null` to draw its has-note dot, so gating day keys the same way would collapse "disabled" and "enabled but no note" into one absent key and the dot could no longer tell them apart.

The second is anywhere `date` is a `Moment` that came from a `CacheEntry`. The index holds entries **by reference**, and several Moment methods mutate in place — `.weekday()` most sharply. A token or handler that mutates its argument silently moves the entry off the key it is indexed under, and nothing fails loudly. `applyTemplateToFile` clones before rendering, `applyTemplate` clones again before `.weekday()`, and `Nav.svelte` normalises with `.startOf("month")` before paging so the day component does not drift through short months. All three are the same rule.

The third is moment's **case-sensitive unit aliases**, where `M` is month and `m` is minute. The token patterns are case-insensitive so `{{Month}}` works, which means a lowercase `m` arrives indistinguishable from an uppercase one; `replaceGranularityTokens` reads it as months for month and year tokens and leaves moment's own reading for date and time tokens, so `{{date-30m}}` really is thirty minutes. Anyone simplifying that conditional will break one of the two.

## Uncertainties and tensions

Split by whether I am inferring intent or reporting a known gap.

**Inherited design, intent inferred from code.** `validateFormat` only round-trips the formatted sample through a strict parse for `granularity === "day"`; week, month and year formats are checked for illegal characters and traversal but never for parseability. I cannot tell whether that is a deliberate concession to formats like `gggg-[W]ww` or an unfinished generalisation. `resolveMomentLocale`'s `en → en-gb` entry is **unreachable for exactly the users it was written for** — the system locale wins whenever it shares a prefix with Obsidian's language, so an `en` Obsidian on an `en-US` system gets `en-us`. The comment says it is left as it behaves deliberately, since reviving it would move the calendar's first column from Sunday to Monday, but that is a rationalisation of current behaviour rather than evidence of original intent. And `getPossibleFormats`' partial candidate is slightly looser than the case it exists for: with `YYYY/YYYY-MM-DD` configured, a flat `daily/2026-06-12.md` sitting in the folder root also matches, though the format says notes live in a year subfolder.

**Known and unfixed.** `CacheIndex.has()` has **no production caller** — only tests — and is leftover API surface. `template.test.ts` tests `templateRender.ts`, not `template.ts`; the file kept its name when the pure core was split out.

**The Naur-shaped risk, stated plainly.** This theory was built in a single pass, and the recent history it describes is nearly all one author's: eighteen of the last twenty-four commits are milestone work from one sequence. Very little here "resisted easy explanation" to me, which is exactly the condition under which a theory looks more settled than it is. The dense comments throughout the code are unusually good and carry much of the reasoning above — but comments record conclusions, not the alternatives that were rejected, and no second maintainer has yet tried to change this system and found out which of these claims they actually needed.
